## The theme

**1.0 proved the product worked. 1.1 answers what happened when strangers arrived.**

The LinkedIn launch measured the funnel honestly: **5,000 views → 150 reactions → 15 signups → 10
résumé uploads**. Google login plus a résumé upload sat in front of every job in the database, so
roughly 99.9% of the interest the product generated never saw a single posting. Meanwhile the users
who *did* get in were reading a dashboard whose location column sorted every Workday row under **U**,
in a browser tab with no icon, off a pipeline that only refreshed once a day.

So this update is three strands, in this order of importance:

1. **Open the funnel** — vertical switching, then a login-free demo board (the block in `docs/20`).
2. **Make what a stranger sees read well** — favicon and manifest, normalized locations, honest copy.
3. **Make it fresher and cheaper** — the pipeline goes 4-hourly while the digest stays daily.

The strands are not independent. Switching had to ship *before* the demo, because a demo that lets a
visitor browse four verticals and then hands them an irreversible one-time choice teaches the opposite
of what the product does. Hayden's rule: **if we don't allow it at signup, we can't allow it in the
demo.**

### 1 · The digest links back to the dashboard (#111, D-102)

Every digest email now carries `{VJA_PUBLIC_BASE_URL}/dashboard` directly under the heading, in both
bodies. It is the email's only Rolefeed-origin link besides unsubscribe, and it sits *above* the roles
so a large closure rollup cannot bury it. `/dashboard` rather than `/`, because a logged-out click
routes through `/login` and back, while `/` would show a returning reader the landing page.

Gated on the public origin alone — unlike the unsubscribe footer it needs no `users` row, so a
pre-login seed profile gets the link without the footer, and a dev run never emits a localhost URL.

### 2 · The pipeline goes 4-hourly, the digest stays daily (#112, D-103)

The largest operational change in the update, and it supersedes D-005's once-daily fetch. Two Cloud
Run Jobs on two schedules: `vja-nightly --no-digest` runs fetch → diff → extract → match at
`0 1,5,9,13,17,21` America/Chicago, and `vja-digest` sends at `0 6`. Without the flag `vja-nightly`
still composes the whole loop including the send — **the flag *is* the split**, and dropping it in
deploy config would send every user six digests a day.

**The digest needed no window change**, which is the detail that made this cheap: `build_digest`
resolves `since` to `last_sent_at` for that recipient, not to a fixed 24 hours.

Also shipped here: the skip-if-running guard (`RUN_STALE_AFTER` 4h, a check and not a lock, skipping
*before* Layer 2 so a racing run cannot pay the strong model twice), `postings_reopened` on
`pipeline_runs`, `VJA_PIPELINE_MAX_MATCHES` as a per-run per-profile cap that defers rather than
refuses, and a deterministic freshest-first order on `postings_needing_match` — without which every
count-capped caller was slicing a set the database could return in any order it liked.

**Measured, and the reason this was worth doing:**

| | Before (daily) | After (4-hourly) |
|---|---|---|
| LLM spend | $4.29 (07-27), $5.52 (07-28) | $1.64 across 07-29's four runs |
| Reopens | 136 in one 07-29 pass | 105 across eight 07-30 runs |
| Grid digest closures | 280 | 227 |
| Run duration | — | 12-23 min inside a 240-min window |

Cost fell rather than multiplied, exactly as the ADR argued: extraction is `content_hash`-cached and
matching excludes already-matched postings, so the same postings cost the same, just discovered sooner.
The churn numbers falling is the more interesting result — shorter windows catch fewer board artifacts.

### 3 · Pre-launch sweep (#113)

No feature work; a deliberate pass over code and production logs before inviting more users. Three
findings worth remembering:

- **Camus Energy had silently gone dark and it was an ATS migration, not a death.** 100% fetch failure
  since 2026-07-28T11:04Z; their careers page still carried a stale Greenhouse embed beside a live
  Rippling board. Repointing the seed row was **config-only, zero `src/` change** — D-004 holding for
  *attrition* rather than for a new vertical, which is a use it had not been tested on. Verified in
  prod the next morning: the 02:00Z run fetched `camus-energy` through Rippling, `fetched=4 new=4`.
- **`alerts.sh` cannot express an edit.** It is idempotent by `displayName`, so changing a policy's
  window and re-running is a silent no-op that looks like success. Production ran the pre-D-103 26h
  nightly absence window for a day this way. The policies had to be deleted first, then re-created.
  Now written into INVARIANTS, because it will recur.
- **`vja-digest` had never run once.** Its logic was old and well-proven, but the *Job's container
  path* — entrypoint override, Neon connect, secret mount — was completely unexercised, and its first
  attempt would have been unattended, at 06:00, to real users. Smoked with `--args=--vertical=__smoke__`
  (an unknown vertical makes the send loop body unreachable), exit 0, zero emails.

### 4 · Honest copy on the matching banner (#114)

**Beta feedback: new users thought the app was broken.** They signed up, landed on the dashboard, saw
no matches, and read only *"Matching in progress. Results update live."* The banner now quotes an
honest 5-to-20-minute range against measured 6-25 minute production backfills, and tells the user to
**keep the tab open**.

Both halves are load-bearing rather than decorative. Promising "a few minutes" to someone still waiting
at minute 12 reproduces the bug being fixed. And the instruction to keep the tab open is infrastructure
leaking into copy on purpose: the dashboard's ~10s poll is what keeps the Cloud Run instance warm, and
Cloud Run cannot see background work when scaling down, so a closed tab can starve the very backfill
the user is waiting on. That coupling now lives in INVARIANTS rather than in a code comment.

### 5 · Vertical is now self-serve switchable (#115, D-104)

`PATCH /api/me {vertical}` → `switch_vertical`, a Settings control behind a confirm dialog, and one
additive migration (`users.last_vertical_switch_at`). Supersedes D-064's immutability. It re-files the
user's **existing `resume_text`** under the target vertical — never a re-upload — and schedules the same
background backfill a signup does. `POST /api/profiles` still 409s a cross-vertical *upload*, because
silently moving a vertical from a file upload is worse than an error.

Three things worth carrying forward:

- **Most of it was already supported.** `profiles` was already keyed `(user_email, vertical,
  resume_version)` with an `active` flag, `last_sent_at` keys on `(vertical, recipient)` so the digest
  needed zero work, and `resume_text` already lived on the profile row. One line forbade the feature.
- **The correctness trap:** `_upsert_profile` deactivates only the *target* vertical's other versions,
  so a switch must explicitly deactivate the old one or the user goes active in two verticals and the
  nightly matches and bills them in both. Pinned by `test_switch_deactivates_the_old_vertical`.
- **The 24h clock protects signups, not spend.** Cost is structurally bounded — matching is idempotent
  per `(posting, profile, resume_version)` and a revisit reactivates the same row — so worst case is
  ~4 × `VJA_BACKFILL_MAX_POSTINGS` per résumé version, then exhausted. The clock exists so one user
  cannot exhaust the global signup ceiling and 429 other people's signups, which is why it is charged
  **only when the switch creates work**.

### 6 · The public `/demo` board (#116, D-105)

The funnel fix itself. `/demo` **is** the dashboard rendered logged-out — same subbar, table, panel and
live rows — with matching *replaced* in its three places rather than removed: the match column keeps its
header and offers sign-in per row, the panel's match slot reads "Log in to view your matches", and
*Matched for you* stays visible but routes to `/login`. Never fabricated. Dropping those would have
produced a smaller, different product that never shows a visitor what signing in buys.

**The anti-leak guarantee is structural at two independent layers**, which is the part worth
remembering: `dashboard_statement(profile_id=None)` builds SQL that never references `matches` (pinned
by compiling it and asserting the table name is absent), and the public endpoints serialize
`PublicPostingRow`, which does not *declare* `verdict`/`score`/`fits`/`gaps`/`rationale`. D-067's
`VJA_AUTH_REQUIRED` is untouched; anonymous `/api/postings` still 401s.

**Caching is the abuse guard** — there is no rate limiting anywhere in the app. A per-process TTL cache
on `(vertical, window)` plus `Cache-Control: public, max-age=300, s-maxage=900`.

Riding along, and a real palette change: **red became the error family, not the deletion-only family.**
`.notice.error` had been styled as accent-lavender text, indistinguishable from ordinary muted copy, so
the "one vertical switch per 24 hours" 429 read as a footnote rather than as the reason nothing happened.

### 7 · Rolefeed has a favicon (#117)

`frontend/index.html` had a `<title>` and nothing else, so every tab, bookmark and phone home screen
showed the browser's blank-page glyph. Survivable while the only visitors were logged-in beta users;
not survivable once `/demo` and a crawler-inviting `robots.txt` put a blank tab on the funnel's *first*
impression.

Two things the generator got wrong and shipping verbatim would have kept: favicon.io emits `name` and
`short_name` as **empty strings** and both colours as `#ffffff` — white, against a dark-only design
language. Now `Rolefeed` at `#08090c`, the `--bg` token, plus a matching `<meta name="theme-color">`.

That colour now lives in four places and **structurally cannot live in one** — neither an HTML attribute
nor a JSON manifest can read a CSS custom property. So `src/favicon.test.ts` pins the duplication
instead, parsing `--bg` out of `theme.css` and asserting the meta tag and both manifest colours equal it.
A broken icon path is otherwise silent: tests pass, the build succeeds, and the tab is blank.

### 8 · US locations normalized for display (#118, D-106)

The closing item. `postings.location` rendered whatever the board wrote, and a survey of the dev corpus
(12,010 rows) found the same place written four ways: `Olathe, Kansas` beside `Kinston, NC`, plus
`USA - Seal Beach, CA`, `Atlanta, GA, United States`, `US, Dayton, OH`,
`West Palm Beach, FL, US, 33407`. Sorting the location column put every Workday `USA - …` row under
**U**; filtering for a state found half the rows.

**Display-only**, as `vja.comp` → `comp_display` already was: `vja.location.us_location_display` is a
bottom-layer pure function surfaced as `location_display` on both `PostingRow` and `PublicPostingRow`.
The stored value stays L1-authoritative and ships beside it, so there is **no migration, no Neon run,
and no backfill over 12k rows**. The digest body reads the normalized string while the audit blob keeps
the raw one.

**Expansion, not contraction**, and the collision was measured rather than guessed: in 12,010 rows
exactly **three** would be mangled by naive expansion (`Gurugram, IN`, `Buenos Aires, AR`, `Bogota, CO`),
because most countries these employers post from carry codes that are not US states at all. That sized
the guard: an explicit US mention settles it, a non-ISO code cannot be a country, else the preceding
city must not be a known foreign one. `DC` never expands. Deliberately **not** title-cased —
`OAKBROOK TERRACE` stays shouty rather than risk `McLean`, `NASA Ames` and `IBM`.

Validated against the real corpus, not just fixtures: 377 distinct strings change, 2,304 postings are
touched, and the 148 changes carrying no US mention were checked one by one.

## Known and not fixed

Named deliberately, carried into 1.2. Each is a decision, not an oversight.

- **Dead apply links now go public.** D-008 verification runs pre-digest only, so the dashboard and
  `/demo` are unverified, and a permanently dead board stays `open` forever (a failed fetch mutates
  nothing, so its postings never close). A stranger's first impression is exactly where "one fake
  posting costs more trust than ten real ones earn" bites hardest. Named in D-105 and left to its own
  session rather than bundled into the demo PR.
- **The digest `new`-window hole.** `build_digest` picks `new` as `first_seen_at > last_sent_at`
  INNER-JOINed to a match row, and the window only ever moves forward, so a posting first seen *before*
  a digest but matched *after* it can never appear in any digest. Two routes in: a per-posting match
  failure (pre-existing since Phase 5) and D-103's `VJA_PIPELINE_MAX_MATCHES` deferral (new). The fix is
  one WHERE clause and no migration. **Not observed in production** — the largest post-split run matched
  33 across ten profiles against a cap of 400.
- **Two D-106 location residuals**, both measured and both pinned by tests so a future change is
  deliberate: boards writing `Country - State - City` lose the country but keep their dash order (80
  postings corpus-wide, 1 in-scope and open), and an *unlisted* foreign city paired with its own country
  code still reads as a US state — the same coarse-gate residual `prefilter` documents for "Munich, DE".
- **`.cell-location` has no truncation.** Full state names widen the column. Multi-site rows were
  already long, so this adds length to an existing category rather than creating a new one, but it is
  untested against a human eye.
- **`alerts.sh` cannot express an alert-policy edit** (above). Any future window or wording change needs
  a delete before the re-run, and nothing in the output says it skipped.
